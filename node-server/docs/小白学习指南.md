# node-server 小白学习指南

> 面向第一次接触本仓库 Node 后端的同学。  
> 目标：搞懂「这个服务是干什么的 → 目录怎么分层 → 一次请求怎么走 → 该按什么顺序读代码」。

---

## 0. 先建立直觉：这个服务解决什么问题？

想象你有一堆公司文档（PDF、Word、Markdown）。用户问：

> 「报销流程是什么？」

如果直接把问题丢给大模型，它可能胡编。**RAG（Retrieval-Augmented Generation，检索增强生成）** 的做法是：

1. **先入库**：把文档切成小段（chunk），存进数据库，并做成向量。
2. **再检索**：用户提问时，先找出最相关的几段原文。
3. **再回答**：把「问题 + 相关原文」一起交给大模型，让它基于证据作答。

本服务（`node-server`）就是做这件事的 **HTTP 后端**：

- 文档上传 / 文本入库
- 切分、向量化、混合检索
- Agent 问答（可调用「搜知识库」工具）
- 会话历史、健康检查

它与仓库里的 Python `server/` 对齐接口，前端默认请求：

```text
http://localhost:8000/api/v1
```

## 1. 你会用到哪些「零件」？

| 零件 | 作用（小白版） | 本项目里谁管 |
|------|----------------|--------------|
| **Express** | 接收 HTTP 请求、返回 JSON | `app.ts` / `api/*` |
| **PostgreSQL** | 存文档元数据、chunk 正文、问答日志 | `core/postgres.ts` + `models/*` |
| **Milvus** | 存向量，做语义相似检索 | `core/milvus.ts` |
| **Redis** | 缓存/会话预留（健康检查会探活） | `core/redis.ts` |
| **DashScope（通义）** | 大模型聊天 + 文本向量 | `core/llm.ts` / `core/embeddings.ts` |
| **BM25** | 关键词检索（内存索引） | `rag/bm25_index.ts` |
| **Zod** | 校验请求体是否合法 | `schemas/*` |

一句话分工：

- **Postgres** = 真相来源（结构化数据）
- **Milvus** = 语义搜索引擎
- **BM25** = 关键词搜索引擎
- **LLM** = 会说话的大脑
- **Agent** = 大脑 + 会自己决定何时「搜知识库」

## 2. 目录地图（先认路，再读代码）

```text
node-server/
├── src/
│   ├── main.ts              # 程序入口：预热 → 监听端口
│   ├── bootstrap.ts         # 启动预热：建表、目录、客户端
│   ├── app.ts               # Express 工厂：中间件 + 路由 + 错误处理
│   ├── config/settings.ts   # 读 .env，集中配置
│   ├── api/                 # 路由层：只负责 HTTP 进/出
│   ├── schemas/             # 请求/响应形状（Zod）
│   ├── services/            # 业务编排：把多步流程串起来
│   ├── models/              # 表结构 + SQL CRUD
│   ├── rag/                 # RAG 核心：加载、切分、入库、检索
│   ├── agent/               # Agent：ReAct 循环、工具、记忆
│   ├── core/                # 基础设施客户端：PG / Redis / Milvus / LLM
│   ├── middleware/          # 如请求耗时
│   └── utils/               # 日志、SSE、文件存储等
├── .env.example             # 环境变量模板
├── package.json
└── docs/小白学习指南.md      # 本文件
```

### 分层怎么理解？（非常重要）

建议把调用关系记成：

```text
HTTP 请求
  → api/          （解析参数、选状态码、返回 JSON）
    → services/   （编排业务流程）
      → rag/ / agent/ / models/   （真正干活）
        → core/   （连外部系统）
```

**不要**在 `api/` 里直接写一大段 SQL 或向量逻辑；本仓库已经按这个分层拆好了。

## 3. 服务是怎么启动的？

阅读顺序：`main.ts` → `bootstrap.ts` → `app.ts`

### 3.1 `main.ts`（大门）

1. 配置日志  
2. `warmUpSingletons()` 预热  
3. `createApp()` 创建 Express  
4. `listen(8000)` 开始接请求  
5. 收到 Ctrl+C 时关闭 Redis / Postgres 连接池

### 3.2 `bootstrap.ts`（开工前热身）

启动时尽量准备好：

1. Postgres 连接池 + 建表（document / chunk / query_log）
2. 上传目录 `storage/uploads`
3. Redis / Milvus 客户端对象
4. BM25 索引管理器
5. Agent 短期记忆（进程内 Map）

注意：预热 **失败不阻断启动**，真正通不通看 `GET /health`。

### 3.3 `app.ts`（装配车间）

- CORS、JSON 解析、耗时中间件
- 挂载 `GET /health`
- 挂载 `/api/v1` 业务路由
- 统一错误处理 → `{ detail: "..." }`

## 4. 两条主航线：写入 vs 问答

整个系统可以先只记住两条路。

### 航线 A：文档入库（Write Path）

```text
上传文件 / 贴文本
  → api/documents.ts
    → DocumentService.ingestText / ingestFile
      → rag/loader.ts          # 解析成 LoadedDocument（sections）
      → rag/ingest.ts          # 切分 → 写 Postgres → 写 Milvus
      → bm25 markDirty         # 标记词法索引需要重建
```

核心函数：`ingestLoadedDocument`（在 `rag/ingest.ts`）

五步心法：

1. 创建/更新 `document` 行（status=`uploaded`）
2. 按 section 选 splitter 切成 chunk
3. `insertChunks` 写入 Postgres
4. 向量化写入 Milvus，回填 `vector_id`
5. 更新 `chunk_count`、status=`indexed`（或无 chunk 时 `parsed`）

**事务提醒**：API 外层常用 `withSession`，保证 Postgres 多步写入要么全成功要么全回滚；Milvus 不在同一事务里。

### 航线 B：问答 / 检索（Read Path）

```text
用户提问
  → api/chat.ts 或 api/retrieval.ts
    → ChatService / RetrievalService
      → rag/retriever.ts       # 向量 + BM25 + RRF 融合
      → agent/graph.ts         # ReAct：思考 → 调工具 → 再思考
      → 返回答案 + 溯源片段
```

检索器要点（`rag/retriever.ts`）：

1. 向量检索（语义相似）
2. BM25 检索（关键词）
3. **RRF** 把两路结果融合排序
4. 都空时回退 Postgres `ILIKE`

Agent 要点（`agent/graph.ts`）：

- 自实现 ReAct 循环（不是直接用 LangGraph createAgent）
- 工具：`search_knowledge_base`（搜知识库）
- `thread_id` 绑定多轮短期记忆

## 5. Postgres 连接池与会话（必学）

文件：`core/postgres.ts`

| API | 干什么 |
|-----|--------|
| `getPool()` | 进程内单例连接池（最多约 15 条连接） |
| `withClient(fn)` | 借一条连接执行，结束必 `release` |
| `withSession(fn)` | 在同一连接上 `BEGIN` → 干活 → `COMMIT/ROLLBACK` |

为什么小白也要懂：

- **池**：避免每个请求都新建数据库连接（又慢又容易把库打满）
- **会话/事务**：入库时 document + 多个 chunk 必须原子成功，否则会出现「有文档没内容」的脏数据

业务代码通过 `Queryable`（Pool 或 PoolClient）注入，同一套 `models/*` 既能在事务里跑，也能直接用池跑。

## 6. 数据表心智模型（三张表）

| 表 | 存什么 |
|----|--------|
| `document` | 文档级元信息：文件名、状态、chunk 数、知识库名… |
| `chunk` | 切分后的正文片段 + metadata + vector_id |
| `query_log` | 问答日志：问题、答案、耗时、溯源… |

关系：一个 document → 多个 chunk。  
向量本体在 Milvus；Postgres 的 `chunk.vector_id` 是「指向向量库的钥匙」。

文档状态常见值：

- `uploaded`：刚创建
- `parsed`：解析了但没有可检索 chunk
- `indexed`：切分完成且已向量化，可检索
- `failed`：处理失败

## 8. 本地跑起来（最小可行）

### 8.1 依赖服务

需要本机或 Docker 起好：

- PostgreSQL（如 `5432`）
- Redis（如 `6379`）
- Milvus（如 `19530`）

### 8.2 安装与配置

```bash
cd node-server
pnpm install
cp .env.example .env
```

至少改这些：

- `POSTGRES_DSN`
- `REDIS_URL`
- `MILVUS_URI` / `MILVUS_COLLECTION`
- `DASHSCOPE_API_KEY`

### 8.3 启动

```bash
pnpm init-db   # 可选，启动时 bootstrap 也会建表
pnpm dev
```

验证：

```bash
curl http://localhost:8000/health
```

试入库（示例）：

```bash
curl -X POST http://localhost:8000/api/v1/documents/ingest-text \
  -H "Content-Type: application/json" \
  -d "{\"filename\":\"demo.txt\",\"content\":\"报销需要先提交申请单，经主管审批后财务打款。\",\"knowledge_base\":\"default\"}"
```

试检索：

```bash
curl -X POST http://localhost:8000/api/v1/retrieval/search \
  -H "Content-Type: application/json" \
  -d "{\"query\":\"报销流程\",\"top_k\":5}"
```

试问答：

```bash
curl -X POST http://localhost:8000/api/v1/chat \
  -H "Content-Type: application/json" \
  -d "{\"message\":\"报销流程是什么？\",\"session_id\":\"demo-1\"}"
```

## 10. 读代码小技巧

1. **先跟调用链，再抠细节**  
   从某个 API 路由用 IDE「Go to Definition」一路点进去，比从工具函数反推更快。

2. **分清「编排」和「实现」**  
   - Service：决定先做什么、后做什么  
   - rag/models/core：具体怎么做

3. **日志关键字**  
   - `[INGEST]` / `[SPLITTER]`：入库  
   - `[DOC]`：文档服务  
   - Agent / retrieval 相关 logger：问答与检索

4. **对照 Python 版**  
   本 Node 服务刻意对齐参考 FastAPI 的路径与 JSON 形状；卡住时可以对照仓库 `server/`（或 README 提到的参考实现）看同一概念在 Python 里怎么写。

5. **改代码时的安全区**  
   - 想练手：从加日志、加注释、读懂一个函数开始  
   - 动事务 / 向量回填时要小心数据一致性

## 11. 常见卡点 FAQ

### Q1：服务起来了，但 `/health` 里 postgres 失败？

检查 `.env` 的 `POSTGRES_DSN`、数据库是否已创建、账号密码端口是否正确。

### Q2：入库成功了，检索却搜不到？

常见原因：

- Milvus 未就绪或 collection 不对  
- embedding 模型/维度配置不一致（`MILVUS_DIMENSION`）  
- 文档 status 不是 `indexed`  
- BM25 还未重建（通常检索时会按脏标记重建）

### Q3：聊天没有引用知识库？

Agent 可能没触发工具，或检索结果为空。先用 `/retrieval/search` 确认库里确有相关 chunk。

### Q4：上传大文件失败？

看 `MAX_UPLOAD_SIZE_MB`；超限会走 Multer `LIMIT_FILE_SIZE` → HTTP 413。

### Q5：为什么有的逻辑在 service，有的在 rag？

- `services`：面向「业务用例」（入库文档、聊天一轮）  
- `rag`：面向「RAG 算法流水线」（切分、检索融合）  
两者都需要时，service 调用 rag。
